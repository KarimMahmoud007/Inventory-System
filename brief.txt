

INVENTORY MANAGEMENT SYSTEM — PROJECT BRIEF
==============================================

STACK:
  - Python 3.x + PySide6 (Qt for Python)
  - SQLite3 (via QSqlDatabase/QSqlRelationalTableModel and QSqlQuery)

ARCHITECTURE PATTERN: Modified MVC (Model-View-Controller)
  Models  → database CRUD logic (QSqlRelationalTableModel or raw QSqlQuery)
  Views   → PySide6 QWidget subclasses (UI + signals)
  Controllers → business logic, signal wiring between model & view
  The main_window.py serves as a "front controller" that wires sidebar navigation AND
  owns model creation: all models are instantiated once in MainWindow and injected into
  the controllers (dependency injection). The single StockBatchModel is shared by both
  OrderModel and BatchController (the batch child that StockController owns and forwards
  the injected instance to).

DATABASE SCHEMA (schema.sql):
  stock          — id, name, unit_of_measure (FK→units.id)  (product definitions, no batch data)
  stock_batch    — id, stock_id (FK→stock.id ON DELETE RESTRICT), price, production_date, expiration_date, quantity, status (available/out_of_stock), added_at
  items          — id, name, available, price  (finished products/recipes)
  items_recipe   — id, item_id (FK→items.id), stock_id (FK→stock.id), amount, unit (FK→units.id)  (recipe ingredient link)
  wasted_stock   — id, stock_batch_id (FK→stock_batch.id), wasted_amount, unit (FK→units.id), price, waste_type, wasted_at
  orders         — id, created_at, status (draft/placed/cancelled/fulfilled), subtotal, cost  (order header; subtotal=revenue, cost=ingredient cost)
  order_items    — id, order_id (FK→orders.id ON DELETE CASCADE), item_id (FK→items.id), quantity  (one row per recipe ordered)
  order_batch_consumption — id, order_id (FK→orders.id ON DELETE CASCADE), stock_batch_id (FK→stock_batch.id), amount, unit_price  (finance ledger: one row per batch consumed by an order; orders.cost = SUM(amount*unit_price); line cost is derived, not stored; index idx_obc_order on order_id)
  units          — id, name (seed: kg, mL, L, g)  (reference)
  inspector_state — name (PK), last_run_on (TEXT 'YYYY-MM-DD')  (InventoryInspector calendar schedule; created on demand by the inspector too, so an existing DB needs no migration — and an older last_run_at REAL table is dropped/recreated by the same code)

Seeded data: units → [(1,'kg'), (2,'mL'), (3,'L'), (4,'g')]

KEY PATTERNS / CONVENTIONS:
  1. Signal-based communication  (views emit signals → controllers handle → models update)
  2. QSqlRelationalTableModel + QTableView for stock items (FK display via setRelation)
  3. QSqlTableModel + QTableView for stock batches (filtered by stock_id)
  4. QSqlQuery for custom queries (recipes catalog, recipe get/update)
  5. Named singleton DB connection via create_qt_connection() / QSqlDatabase::contains()
  6. QStackedWidget sidebar navigation (MainWindow.page_map dict)
  7. Controller-internal QStackedWidget for two-level stock navigation (items → batches), now split across two controllers: StockController owns the stack + item_view (Level 1), its child BatchController owns the batch page (Level 2) and is passed that same stack + item_view to navigate
  8. ObjectName-based Qt stylesheets for custom widget styling
  9. StockMode/BatchMode/RecipeMode enums to control form behavior (INSERT vs UPDATE/EDIT)
 10. No .ui files — all UI created programmatically in Python
 11. Cached data in BaseModel: @staticmethod @lru_cache get_units()/get_catalog()/get_recipes_catalog(), instance properties that read from cache, invalidate_*() methods to refresh
 12. Dataclass entities (StockItem, StockBatch, RecipeItem, Recipe) for type safety across signals, models, validation, and forms
 13. Views expose show_warning(title, message) — controllers call it instead of QMessageBox directly
 14. Views receive data via constructor params (injected by controller) — no direct imports of cached functions from utilities or models
 15. Transactional recipe save/update (db.transaction + commit/rollback)
  16. Recipe update: UPDATE items header, UPSERT items_recipe rows by id (UPDATE existing, INSERT new, DELETE removed)
  17. All destructive/edit operations use PK-based QSqlQuery (WHERE id = ?) instead of row-index-based model access — safe under any sorting/filtering
 18. FK enforcement is enabled on the Qt connection (create_qt_connection runs "PRAGMA foreign_keys = ON" after open — per-connection, so required at runtime; schema.sql's pragma only covers the sqlite3 setup connection)
 19. Stock delete is DB-enforced: stock_batch.stock_id is REFERENCES stock(id) ON DELETE RESTRICT. delete_stock_item lets the DELETE fail and, on FK violation, emits item_delete_rejected(str) instead of querying for batches first. The detection is StockModel._is_fk_violation: ON DELETE RESTRICT is enforced through an internal trigger and surfaces as nativeErrorCode 1811, NOT the 787 a direct FK violation gives — the old 787/19-only check never matched, so the rejection message never reached the user. Codes 19/787/1811 are accepted plus a 'FOREIGN KEY' text backstop, since extended codes vary by SQLite build
 20. Stock insert rejects duplicate names: insert_stock_item runs an in-code case-insensitive check (name = ? COLLATE NOCASE, trimmed) and emits item_insert_rejected(str) if a match exists
 21. Rejection signals (item_delete_rejected / item_insert_rejected) carry a user message; StockController wires them to view.show_warning (StockWindow now exposes show_warning; StockItemFormWindow already did)
 22. Order dry-run: OrderModel.validate_stock expands order items → recipe ingredients (items_recipe) → sums required per stock item → compares against cached BaseModel.get_available_stock(stock_id). Pure read, touches no real stock. Returns ValidationResult(ok, shortages, errors). The recipe→ingredient expansion (_recipe_requirements) is a thin wrapper over the cached BaseModel.get_recipe_requirements(item_id) — invalidated by invalidate_recipe_requirements() on recipe save/update (recipes_model) AND on every stock mutation (stock_model.sync_model, since the cached stock_unit/name would otherwise go stale and corrupt unit conversion).
 23. Available-stock cache: BaseModel.get_available_stock(stock_id) is @staticmethod @lru_cache (sum of available stock_batch.quantity in the item's own unit). Invalidation is EXPLICIT via invalidate_available_stock() (.cache_clear()) after every committed stock mutation — called by OrderModel.place_order (post-commit) AND by all StockBatchModel mutators (insert/update/delete/toggle). All stock writes go through StockBatchModel or OrderModel, so the cache cannot go stale; this is the single serialized stock-mutation path.
 24. FIFO/oldest-batch-first deduction: OrderModel._deduct_for_order gets each ingredient's available batches (quantity>0, ORDER BY added_at ASC, id ASC) via StockBatchModel.get_available_batches, deducts from the oldest, rolls the remainder to the next, and passes the consumed amount to StockBatchModel.deduct_batch, which subtracts it and flips a depleted batch to status='out_of_stock'. Both read and write go through the shared batch model's public API (not raw SQL in OrderModel). Runs inside place_order's db.transaction() — deduct_batch shares the connection, so it joins the transaction (rollback on any failure → no partial deduction). It returns a list[BatchConsumption] (stock_batch_id, stock_id, amount, unit_price) instead of a cost — see #31.
 25. Unit conversion (Utilities/units.py): recipe ingredient amounts (items_recipe.unit) are converted into the stock item's unit_of_measure before compare/deduct. Cross-dimension (e.g. g↔L) or unknown units raise ValueError → surfaced as fail-loud errors in ValidationResult.errors (place blocked). Recipes with no items_recipe mapping also fail loudly (not silently skipped).
 26. Order draft is in-memory only (OrderController.draft); leaving/closing the page discards it without touching stock. Counter changes trigger a debounced (QTimer single-shot) dry-run that enables/disables Place Order and shows inline shortages.
 27. Order financials: subtotal = revenue = Σ(recipe price × quantity), where the recipe price is read from the cached recipes_catalog (BaseModel.get_recipes_catalog) — no per-item items-table query; cost = Σ(amount consumed from each batch × stock_batch.price) computed by FinanceModel (#31), where stock_batch.price is the per-single-unit cost. Because deduction is FIFO, cost is the exact sum over the consumed (oldest) batches. profit = subtotal − cost. Both subtotal and cost are stored on the orders row at placement (UPDATE inside place_order's transaction); profit is display-only (computed in OrderController._on_order_placed for the popup). Cost and profit are NOT estimated live — only subtotal is shown live during editing.
 28. Live dry-run vs finalized: validate_stock (dry-run) attaches only result.subtotal (live revenue) — there is no live cost/profit estimate. The summary panel shows Subtotal while editing; Cost and Profit appear only in the post-placement popup, computed from the exact FIFO deduction (OrderModel._deduct_for_order returns the total cost or None on failure). _required_by_stock(order) is the shared per-stock requirement aggregator used by validate_stock and _deduct_for_order.
 29. Order page live refresh: StockController and RecipesController each expose a data_changed Signal. StockController emits it on item insert/update/delete; batch insert/update/delete/toggle now flow through BatchController.data_changed (those batch_* relays are wired once in BatchController.__init__ since the batch model is persistent/injected) which StockController relays up through its own data_changed; RecipesController emits it on recipe save/update. MainWindow (front controller) relays both to OrderController.refresh_current_order(), which rebuilds the recipe list (set_recipes), reconciles the in-progress draft (drops recipes that no longer exist, refreshes names — preserving quantities), and re-runs the dry-run. Counter restore uses RecipeOrderRow.set_quantity() which sets the value silently (no quantity_changed emit) to avoid feedback loops.
 30. Model dependency injection: all models (StockModel, StockBatchModel, RecipesModel, OrderModel) are created once in MainWindow.__init__ and passed into the controllers' constructors; controllers no longer construct their own models. The single StockBatchModel is injected into BOTH OrderModel(batch_model=...) and BatchController (StockController receives it and forwards the same instance to the child it constructs), so every stock_batch read/write across the app goes through one persistent instance (the single serialized stock-mutation path of #23). Because BaseModel._shared_db is a singleton, all models still share one DB connection regardless of who created them.

 31. Finance owns the cost: OrderModel INSERTs the order with cost left at the schema default 0 and writes only subtotal; it then hands the deducted batches (list[BatchConsumption]) to FinanceModel.apply_order_cost(order_id, consumptions), which INSERTs one order_batch_consumption ledger row per batch and UPDATEs orders.cost = Σ(amount × unit_price). FinanceModel opens no transaction and shares BaseModel._shared_db, so it joins place_order's transaction — a failure anywhere rolls the whole thing back, and no order is ever committed with a stale cost of 0. OrderModel no longer computes money beyond the subtotal; the cost math lives in the pure module-level finance_model.total_cost() (covered by test_finance_cost.py).
 32. Finance caches: FinanceModel.get_orders_summary()/get_totals()/get_order_cost_breakdown(order_id) are @staticmethod @lru_cache like the BaseModel reads (tuples, not lists, so they stay immutable). All three are cleared by invalidate_finance(), called by OrderModel.place_order post-commit alongside invalidate_available_stock(). The Finance page refreshes off OrderModel.order_placed_successfully (wired in MainWindow to FinanceController.refresh) — the model's signal, not the order controller's, so Finance does not depend on the order UI.

 33. InventoryInspector (models/inventory_inspector.py): the app's only push-based read. One instance watches one SQL query. Two modes off one class — with period_days it self-schedules, without one it only runs when someone calls run(). The schedule is CALENDAR DAYS, not elapsed seconds and not app uptime: the last-run DATE is persisted in inspector_state, so a daily watch fires once per day whatever time the app is opened (an interval-of-seconds version drifts later every run and eventually skips days). The constructor calls check_due() immediately so a restart catches up on anything missed while closed, then a QTimer poll (check_seconds, default 10) re-checks in case the app is left open across midnight — a tick is a date subtraction against in-memory state, no query. Dates come from stdlib datetime.date; because date.today() is local, the expiry SQL uses date('now','localtime') so both agree on "today". A last run in the future (system clock moved backwards) counts as due rather than parking the watch. Results go out on triggered(name, rows) only when rows exist; the built-in console print is a ponytail-marked placeholder until a notification feature subscribes. Covered by test_inventory_inspector.py.

 33b. Inspector failure contract: run() returns None on query failure and [] on a successful query with no rows — two outcomes that mean opposite things (broken vs nothing to report), which for a monitoring component must not share a return value. check_due() stamps only when run() did NOT fail, so a broken query stays due and retries on the next tick instead of going quiet for a day; on success the stamp is written before reporting, so a crash mid-report can at worst repeat a run, never skip one. An empty result still counts as a run. The error print is deduped against self._last_error (prints once, again if the message changes, cleared on recovery) so a broken watch doesn't spam every poll. No registry/scheduler service — the caller constructs an instance per watch and must hold the reference (dropping it collects the QTimer and the watch stops silently).

 34. Expiry watches (models/expiry_watches.py): create_expiry_inspectors() builds the two concrete inspectors, and MainWindow holds the returned list — "expired-batches" (expiration_date < date('now')) and "expiring-soon-batches" (date('now') <= expiration_date <= date('now', '+7 day'), the window bound as a parameter, not interpolated). Both filter to status='available' AND quantity > 0, since an expired batch nobody can sell is not news, and the two sets are disjoint by construction (today's date counts as "soon", never "expired"). Both use date('now','localtime') to match the scheduler's local date.today(). They run once per calendar day and, because InventoryInspector checks on construction, a batch that expired while the app was closed is reported at the next startup. MainWindow holds them so their QTimers survive, and MainWindow.closeEvent stops them. They live outside StockBatchModel because monitoring shares nothing with batch CRUD or the order-path API except the connection. Nothing consumes triggered yet — output is the console print.

 35. Form input is parsed before an entity exists: every numeric form field goes through Utilities.validate_data.parse_float(text, field_name) -> (value, error) FIRST, and the form shows a warning and returns on error. The entity validators (validate_stock_item/validate_stock_batch/validate_recipe_item) run on an already-built entity, so they structurally cannot protect the float() conversion that builds it — an empty Price used to raise ValueError inside a Qt slot, which PySide6 >= 6.5 turns into a process abort. BatchFormWindow._field_error() checks Price+Quantity before save() emits; RecipeFormWindow._on_submit_recipe_clicked checks name, price, at-least-one-ingredient, and every ingredient quantity. A recipe with no ingredients is rejected at the form because it can neither be ordered (fail-loud) nor reopened for editing. Covered by test_form_validation.py.

 36. Failed writes are reported, not printed: StockModel and StockBatchModel each expose operation_failed(str) and a private _failed(action, error) that logs AND emits. Every write failure path goes through it, so a failed save can no longer look identical to a successful one. StockController wires it to item_view.show_warning; BatchController._on_operation_failed prefers the open form window and falls back to the batch page. The specific rejections (item_insert_rejected duplicate name, item_delete_rejected FK) still take precedence over the generic signal.

 37. One transaction helper: BaseModel.transaction() is a @contextmanager that runs db.transaction(), commits on success and rolls back on ANY exception (which then propagates). Used by OrderModel.place_order and RecipesModel.insert_recipe/update_recipe. Failure inside a block raises a module-private exception (OrderFailed / RecipeWriteFailed) instead of repeating rollback+emit+return at every failure point — place_order had five such blocks that had already drifted apart. Because all models share one connection, anything called inside the block joins the transaction: that is how FinanceModel.apply_order_cost's ledger writes roll back with the order. SQLite has no nested transactions, so blocks must not nest.

 38. place_order computes the requirement expansion ONCE and threads it through: _required_by_stock + _order_subtotal run once, _check_availability (split out of validate_stock) does the shortage comparison, and _deduct_for_order(required) takes the already-validated dict rather than recomputing it. Previously the deduction re-derived requirements and discarded the error list, which was safe only because validation happened to have run first. The internal re-validation is NOT redundant with the controller's dry-run — that is debounced 150ms and can be stale when Place is clicked.

 39. Qt item models are written by field name, not column number: insert_batch and insert_stock_item use model.fieldIndex("..."), so a schema reorder cannot silently write into the wrong column. The ONE exception is the stock unit column: QSqlRelationalTableModel.setRelation renames the related field (unit_of_measure becomes 'units_name_2'), so fieldIndex returns -1 and the position must be named — StockModel.UNIT_COLUMN, defined next to the setRelation call that creates the coupling. The domain model's Qt item model is self.table (get_stock_table/get_batch_table); "model" alone always means the domain model.
