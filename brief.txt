INVENTORY MANAGEMENT SYSTEM — PROJECT BRIEF
==============================================

STACK:
  - Python 3.x + PySide6 (Qt for Python)
  - SQLite3 (via QSqlDatabase/QSqlRelationalTableModel and QSqlQuery)

ARCHITECTURE PATTERN: Modified MVC (Model-View-Controller)
  Models  → database CRUD logic (QSqlRelationalTableModel or raw QSqlQuery)
  Views   → PySide6 QWidget subclasses (UI + signals)
  Controllers → business logic, signal wiring between model & view
  The main_window.py serves as a "front controller" that wires sidebar navigation.

DATABASE SCHEMA (schema.sql):
  stock          — id, name, unit_of_measure (FK→units.id)  (product definitions, no batch data)
  stock_batch    — id, stock_id (FK→stock.id ON DELETE RESTRICT), price, production_date, expiration_date, quantity, status (available/out_of_stock), added_at
  items          — id, name, available, price  (finished products/recipes)
  items_recipe   — id, item_id (FK→items.id), stock_id (FK→stock.id), amount, unit (FK→units.id)  (recipe ingredient link)
  wasted_stock   — id, stock_batch_id (FK→stock_batch.id), wasted_amount, unit (FK→units.id), price, waste_type, wasted_at
  orders         — id, created_at, status (draft/placed/cancelled/fulfilled)  (order header)
  order_items    — id, order_id (FK→orders.id ON DELETE CASCADE), item_id (FK→items.id), quantity  (one row per recipe ordered)
  units          — id, name (seed: kg, mL, L, g)  (reference)

Seeded data: units → [(1,'kg'), (2,'mL'), (3,'L'), (4,'g')]

KEY PATTERNS / CONVENTIONS:
  1. Signal-based communication  (views emit signals → controllers handle → models update)
  2. QSqlRelationalTableModel + QTableView for stock items (FK display via setRelation)
  3. QSqlTableModel + QTableView for stock batches (filtered by stock_id)
  4. QSqlQuery for custom queries (recipes catalog, recipe get/update)
  5. Named singleton DB connection via create_QtConnection() / QSqlDatabase::contains()
  6. QStackedWidget sidebar navigation (MainWindow.page_map dict)
  7. Controller-internal QStackedWidget for two-level stock navigation (items → batches)
  8. ObjectName-based Qt stylesheets for custom widget styling
  9. StockMode/BatchMode/RecipeMode enums to control form behavior (INSERT vs UPDATE/EDIT)
 10. No .ui files — all UI created programmatically in Python
 11. Cached data in BaseModel: @staticmethod @lru_cache get_units()/get_catalog()/get_recipes_catalog(), instance properties that read from cache, invalidate_*() methods to refresh
 12. Dataclass entities (StockItem, StockBatch, RecipeItem, Recipe) for type safety across signals, models, validation, and forms
 13. Views expose show_warning(title, message) — controllers call it instead of QMessageBox directly
 14. Views receive data via constructor params (injected by controller) — no direct imports of cached functions from utilities or models
 15. Transactional recipe save/update (db.transaction + commit/rollback)
  16. Recipe update: UPDATE items header, UPSERT items_recipe rows by id (UPDATE existing, INSERT new, DELETE removed)
  17. All destructive/edit operations use PK-based QSqlQuery (WHERE id = ?) instead of row-index-based model access — safe under any sorting/filtering
 18. FK enforcement is enabled on the Qt connection (create_QtConnection runs "PRAGMA foreign_keys = ON" after open — per-connection, so required at runtime; schema.sql's pragma only covers the sqlite3 setup connection)
 19. Stock delete is DB-enforced: stock_batch.stock_id is REFERENCES stock(id) ON DELETE RESTRICT. delete_stock_item lets the DELETE fail and, on FK violation (nativeErrorCode 787/19), emits item_delete_rejected(str) instead of querying for batches first
 20. Stock insert rejects duplicate names: insert_stock_item runs an in-code case-insensitive check (name = ? COLLATE NOCASE, trimmed) and emits item_insert_rejected(str) if a match exists
 21. Rejection signals (item_delete_rejected / item_insert_rejected) carry a user message; StockController wires them to view.show_warning (StockWindow now exposes show_warning; AddStockItemWindow already did)
 22. Order dry-run: OrderModel.validate_stock expands order items → recipe ingredients (items_recipe) → sums required per stock item → compares against cached BaseModel.get_available_stock(stock_id). Pure read, touches no real stock. Returns ValidationResult(ok, shortages, errors).
 23. Available-stock cache: BaseModel.get_available_stock(stock_id) is @staticmethod @lru_cache (sum of available stock_batch.quantity in the item's own unit). Invalidation is EXPLICIT via invalidate_available_stock() (.cache_clear()) after every committed stock mutation — called by OrderModel.place_order (post-commit) AND by all StockBatchModel mutators (insert/update/delete/toggle). All stock writes go through StockBatchModel or OrderModel, so the cache cannot go stale; this is the single serialized stock-mutation path.
 24. FIFO/oldest-batch-first deduction: OrderModel._deduct_for_order fetches each ingredient's available batches (quantity>0) ORDER BY added_at ASC, id ASC, deducts from the oldest, rolls the remainder to the next, and flips a depleted batch to status='out_of_stock'. Runs inside place_order's db.transaction() (rollback on any failure → no partial deduction).
 25. Unit conversion (Utilities/units.py): recipe ingredient amounts (items_recipe.unit) are converted into the stock item's unit_of_measure before compare/deduct. Cross-dimension (e.g. g↔L) or unknown units raise ValueError → surfaced as fail-loud errors in ValidationResult.errors (place blocked). Recipes with no items_recipe mapping also fail loudly (not silently skipped).
 26. Order draft is in-memory only (OrderController.draft); leaving/closing the page discards it without touching stock. Counter changes trigger a debounced (QTimer single-shot) dry-run that enables/disables Place Order and shows inline shortages.
